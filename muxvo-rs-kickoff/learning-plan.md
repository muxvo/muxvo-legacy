# AI 时代非技术创始人的架构学习计划

> 来自 6 人圆桌讨论的综合结论。
> 背景：产品负责人在 Muxvo Rust 重构讨论中发现自己无法评估架构提案，希望找到 AI 时代的高效学习路径。

---

## 圆桌讨论（6 人，各持不同立场）

### P1 — 产品实战派

别学了。说句难听的：你花两天和 Claude Code 讨论 GPUI vs Floem，最后翻车的原因不是你"知识不够"，而是你**角色错位**了。你是产品负责人，不是 Rendering Lead。你的工作是定义"20 路终端 60 FPS"这个目标，而不是判断哪个 GPU 渲染管线能达到这个目标。

你的直觉已经很准了——你能闻出 bullshit、能问出尖锐问题。这是花十万块都买不来的能力。缺的不是架构知识，是**验证流程**。你需要的是五个杀手锏问题：

1. 有没有同量级的生产案例？
2. 你引入的依赖里有没有 GPL？跑一遍 `cargo deny`
3. 这个方案的最大风险点是什么？给我写成 ADR
4. 砍掉这个方案，Plan B 是什么？
5. 你的时间估算基于什么假设？

与其花 12 周学 Rust crate 拓扑，不如花 12 小时把这 5 个问题模板化，然后让你的 9 人 AI 委员会每个决策都必须回答。书是 cope，流程才是杠杆。

---

### P2 — 手艺人派

P1 说得好听，但你刚刚**亲身经历了**这个方法论失败的过程。你让 AI 做架构决策，AI 先推荐 Floem，后来又翻转成 GPUI，你完全无法判断哪个对。这不是"问五个问题"就能解决的——因为你**听不懂答案**。

AI 说"GPUI 的 retained scene graph 做 damage tracking"，你无法判断这句话是真知灼见还是胡说八道。这就是为什么你需要**心智模型**，不是成为专家，而是建立最低限度的"骗不了我"的理解。

类比：你不需要会开飞机，但如果你在买一架飞机，你最好知道"涡扇"和"涡桨"的区别，否则销售说什么你信什么。

具体来说，你需要理解三件事：

1. **依赖关系**——为什么一个 crate 选错了会污染整棵树
2. **许可证的传染性**——GPL 如何从一个文件感染整个二进制
3. **抽象层级**——为什么"渲染框架"和"终端模拟器"是两个不同的决策点

这些不是看书能学会的，但也不是"不学"能过关的。

---

### P3 — AI 原生学习派

两位都对，但解法错了。P2 说得对你需要心智模型，P1 说得对看书是低效的。答案是：**用你正在做的 Muxvo-RS 项目本身作为课程**。

具体操作：打开 Claude Code，指着你那份 `architecture.md` 的第 2.1 节问它：

> "假设你是一个想骗我的 AI，GPUI 这段方案里你最可能忽悠我的三个点是什么？"

然后让它自我辩论。再问：

> "如果 GPUI 是错误选择，半年后项目会怎么死？"

让它做红队推演。

你的 muxvo-rs-kickoff 里有 449 个 REQ、20 个 crate、9 人委员会。每周挑一个 crate，让 Claude Code 给你做一个 30 分钟的 Socratic 教学：它解释这个 crate 的职责边界，你挑战它，它用你项目的真实代码举例。12 周下来你过了 12 个 crate，覆盖整个依赖拓扑。

关键原则：**永远从你的真实问题出发**，不要从教科书出发。你不需要学"什么是 ECS 架构"，你需要学"muxvo-bus 的三原语为什么这么设计"。项目即课程，Claude Code 即导师。

---

### P4 — 怀疑论者

P3 的方案有个致命漏洞：**你让 Claude Code 教你判断 Claude Code 的架构建议**。这是典型的裁判兼运动员。

你的 architecture.md 是 Claude Code 写的对吧？现在你让同一个 Claude Code 教你评审这份文档——它当然会说"写得好、设计合理"，因为这是它自己的作品。它有结构性的利益冲突：承认方案有问题 = 承认自己之前犯错。

你需要**独立的验证源**。具体方案：

1. 找一个 Rust 社区的真人（即使付费咨询 2 小时）做一次 architecture review
2. 在 Zed 的 Discord 或 GitHub Discussion 里贴你的 GPUI vendor 方案问问实际使用者
3. 用不同的 AI（Gemini、GPT）做交叉验证——不是因为它们更好，而是不同模型的偏见不同，交集更可能是真话

我不是说不用 Claude Code 学习。我是说，**单一信息源 + 自信满满 = 最危险的组合**。你的防线不能只有一道。

---

### P5 — 最小必要知识派

争论太多了。我直接给结论：非技术创始人管理 AI 写的 Rust 原生应用，**需要且仅需要掌握 7 件事**：

| # | 知识点 | 为什么必须人懂（不能全交给 AI） | 验证方法 |
|---|---|---|---|
| 1 | **依赖树的"上下游"** | L0 crate 被所有人依赖，改一行全重编。你必须知道 muxvo-ids 为什么不能随便改 | 能指着 crate 拓扑图说出层级 |
| 2 | **许可证传染规则** | GPL 感染二进制，MIT/Apache 不感染。AI 可能漏查（已发生过） | 会跑 `cargo deny` 并读懂输出 |
| 3 | **"接口 vs 实现"** | muxvo-terminal-core 是接口，muxvo-pty 是实现。改接口要走评审 | 能区分 PR 改的是接口还是实现 |
| 4 | **性能指标的可测量性** | "快"不是指标，"冷启动 250ms"是指标 | 会看 CI bench 报告的 8 个数字 |
| 5 | **状态持久化的原子性** | 为什么写文件要 tmp+rename。你 Electron 版已经踩过这个坑 | 知道 `muxvo-fs-atomic` 为什么存在 |
| 6 | **"做 vs 借 vs 买"框架** | 自写 term-view（做）vs alacritty_terminal（借）vs vendor GPUI（借+改）| 每个决策能问成本和锁定风险 |
| 7 | **时间估算的锚定偏差** | AI 和人类都倾向低估。17 周 → 实际 28 周就是活证据 | 任何估算乘 2.5，问"上次类似规模实际花了多久" |

**这 7 件事不需要看书。每件 1 小时实操理解，一周搞定。**

## P6 — 综合者：12 周实操计划（最终结论）

### 核心共识

1. **必须学，但只学最小必要集**——P5 的 7 件事是底线
2. **Muxvo-RS 项目本身是唯一教材**——不看书、不看视频、不脱产学习
3. **必须有独立验证源**——防 AI 自我循环（P4 的致命漏洞）
4. **70% 实操 + 30% 验证**，每周 5 小时

### Phase 1：建立防线（第 1–3 周）

#### 第 1 周：依赖拓扑

- **周一 1h**：让 CC 带你走一遍 `architecture.md` 的 crate 拓扑图（§4）
- **周三 1.5h**：手画 20 个 crate 的依赖关系（纸上或 iPad，不用工具）
- **周五 1h**：
  - 产出：你能指着图说出哪些是 L0/L1/L2/L3
  - **验证**：把图贴到 Rust 社区（Reddit r/rust 或 Zed Discord）让真人看 15 分钟

#### 第 2 周：License 实操

- **周一 1h**：跑一遍 `cargo deny`，理解输出
- **周三 1.5h**：**故意**在 Cargo.toml 里加一个 GPL 依赖，看 CI 怎么拦截
- **周五 1h**：
  - 产出：你能在 PR review 时一眼看到许可证警告
  - **验证**：用 Gemini 交叉检查 Claude 给你的许可证解释

#### 第 3 周：五问模板化

- **周一 1h**：把 P1 的五个杀手锏问题做成 Notion/飞书模板
- **周三 1.5h**：对 architecture.md 每个 D1–D16 决策用五问审一遍，让 CC 回答
- **周五 1h**：
  - 产出：一份决策审计表
  - **验证**：让另一个 AI 模型对同一份蓝本挑毛病，记录分歧

### Phase 2：逐 crate Socratic 教学（第 4–9 周）

每周 1 个 crate，固定节奏：

| 日 | 时长 | 做什么 |
|---|---|---|
| **周一** | 1h | CC 讲解这个 crate 的职责、边界、对外接口。你问"用大白话解释" |
| **周三** | 1.5h | 你写 3 个"这个 crate 可能怎么出问题"的场景，CC 回答，你追问 |
| **周五** | 1h | 用另一个 AI 交叉验证，记录分歧 |

**推荐 crate 顺序**（覆盖从基础类型到渲染的完整链路）：

| 周 | Crate | 你会学到什么 |
|---|---|---|
| 第 4 周 | `muxvo-ids` | 为什么 ID 要专门一个 crate；Copy trait 是什么；改 L0 的连锁反应 |
| 第 5 周 | `muxvo-bus` | 为什么要三种通信方式（pub-sub / req-reply / actor）；它们各自什么时候用 |
| 第 6 周 | `muxvo-terminal-core` | 终端状态机长什么样；WaitDetector 怎么判断"在等输入" |
| 第 7 周 | `muxvo-pty` | 什么是 PTY；为什么它在单独的线程跑；SIGCHLD 怎么回事 |
| 第 8 周 | `muxvo-term-view` | 什么是 damage tracking；为什么不每帧重画；scrollback 怎么压缩 |
| 第 9 周 | `muxvo-storage` | SQLite 为什么用 WAL；tantivy 是什么；为什么搜索要单独的引擎 |

**每周三的高杀伤力提问模板**（打印贴墙上）：

1. "假设你是一个想骗我的 AI，这个 crate 你最可能忽悠我的三个点是什么？"
2. "如果这个 crate 选错了技术，半年后项目怎么死？"
3. "这个 crate 的 Plan B 是什么？换掉它要改多少代码？"
4. "你刚才的解释里有没有你不确定的部分？标出来。"
5. "用一个非技术的类比解释这个概念。"

### Phase 3：实战验收（第 10–12 周）

#### 第 10 周：PR Review 实操

- 项目开始后，对第一批 PR 做"产品负责人 review"
- 每个 PR 用五问模板提一个问题，看 AI 能否回答
- **产出**：你能区分"这个 PR 改了接口"和"这个 PR 只改了实现"

#### 第 11 周：模拟架构评审会

- 让 CC 模拟一次"Sprint 0 结束时的架构评审会"
- 你扮演质疑者，CC 同时扮演 9 个委员会成员回答你
- 录下过程，回听自己的提问质量
- **验证**：找一个真人（付费 Rust 开发者 / 社区朋友）看你的提问记录，反馈你哪些问题是好的、哪些是 AI 绕着走了你没注意到

#### 第 12 周：写"知识边界清单"

写一份 1 页纸的清单，三栏：

| 我能判断 | 我不能判断但知道该问谁 | 我永远外包给 AI/专家 |
|---|---|---|
| 这个 PR 改了 L0 还是 L2 | GPUI 的 GPU 管线是否适合 20 路并发 | Rust lifetime / borrow checker 细节 |
| 依赖里有没有 GPL | 自建 rope editor 质量够不够 | wgpu shader 编程 |
| bench 数字有没有退步 | tantivy 的 CJK tokenizer 效果 | 操作系统信号处理 |
| 时间估算是不是太乐观 | wasmtime 的安全沙箱是否真的安全 | 编译器优化 |

**这份清单就是你的长期操作手册。**

## 持续验证纪律（12 周之后也不能断）

- **每周至少 1 次**用不同 AI 模型交叉检查同一个技术问题
- **每月 1 次**找真人（付费 Rust 咨询、社区提问、朋友推荐均可）做 30 分钟验证
- **持续维护**一个"Claude Code 说错过的事"日志——长期积累你的校准直觉

---

## 12 周后的衡量标准

- ✅ 能在 30 秒内看出一个 PR 改的是 L0/L1/L2 哪层
- ✅ 能对任何技术决策问出至少 2 个让 AI 停顿的问题
- ✅ 知道自己知识边界在哪，不会再花两天陷入自己无法评判的架构辩论
- ✅ 有一个"知识边界清单"可以长期使用
- ✅ 有独立验证渠道（真人 + 多模型交叉），不依赖单一 AI

## 哪些知识交给 AI，哪些必须自己懂（P5 的 7 件事 vs 其余全部）

### 🧠 必须自己懂（AI 会犯错或会忽悠的领域）

| 知识点 | 为什么不能全交给 AI |
|---|---|
| 依赖树上下游 | AI 可能把 L0 的改动轻描淡写，你需要自己判断影响面 |
| 许可证传染 | AI 已经漏查过一次 GPL（本次项目真实事故），你是最后一道防线 |
| 接口 vs 实现 | AI 倾向把所有改动说成"小改动"，你需要自己区分改了接口还是实现 |
| 性能可测量性 | AI 说"性能提升显著"时你要追问"显著是多少 ms" |
| 原子写 | AI 可能在压力下用 `std::fs::write` 走捷径，你 Electron 版吃过亏 |
| 做 vs 借 vs 买 | AI 倾向推荐它了解的方案，不是成本最优的方案 |
| 时间锚定偏差 | AI 天然乐观（它不承担 delay 后果），你需要自己校准 |

### 🤖 可以全交给 AI 的领域

| 知识点 | 为什么可以放心交给 AI |
|---|---|
| Rust 语法 / lifetime / borrow checker | AI 写代码比你学语法快 1000 倍 |
| 具体 API 用法（tokio / serde / rusqlite） | 查文档是 AI 的强项 |
| 算法选择和实现 | AI 选 B-tree 还是 HashMap 这种事大概率是对的 |
| CSS / 布局 / UI 细节 | 像素级调整让 AI 做 |
| 测试代码编写 | AI 写 test case 的覆盖率通常不错 |
| Git 操作 / CI 配置 / 打包脚本 | 机械性操作，AI 不会犯人类的粗心错误 |
| 代码重构 / 改名 / 移动文件 | 纯机械变换，让 AI 做 |
| 文档写作 | AI 写初稿你修改，比你从零写快 5 倍 |

### ⚠️ 灰色地带（AI 做初步判断，你做最终决定）

| 知识点 | 怎么分工 |
|---|---|
| 框架选型 | AI 列候选 + 对比表，你用五问质疑，最后你拍板 |
| 架构拆分 | AI 提方案，你画依赖图验证有没有环 / 有没有越层 |
| 安全审计 | AI 做第一遍扫描，真人或另一个 AI 做第二遍 |
| 性能优化方向 | AI 跑 profiler + 给建议，你看 bench 数字判断优先级 |

---

## 一句话总结

**不是让你变成工程师，是让你变成一个 AI 骗不了的产品负责人。**

Muxvo-RS 项目本身就是最好的课程——449 个需求、20 个 crate、每一条都是真实的学习材料。不需要书，需要的是**对着真东西问锐利的问题，然后用独立信源验证答案**。
