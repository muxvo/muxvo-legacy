# M10 CHAT_SYNC – 聊天同步与导出 PRD

> 版本 v1.0 · 适用 Muxvo 重构 · 行数上限 518

## 1. 模块定位

- **一句话**：把 Claude Code / Codex 散落在原生位置的对话整本"镜像"到 Muxvo，并允许用户随时把任意一段对话导出成 Markdown 或 JSON 文件。
- **不用它会怎样**：用户的历史对话只能停留在 Claude Code 自身的有限保留期里（最短约 30 天就会被清理），过期即丢失；想把某段对话发给同事或贴进文档时也只能逐条手动复制。
- **与相邻模块的分界**：
  - 归档同步开关、同步进度反馈、单会话导出、批量导出 属于本模块
  - 三栏（项目 / 会话列表 / 详情）的浏览体验属于 [M08 CHAT_BROWSE]
  - 关键词搜索与高亮跳转属于 [M09 CHAT_SEARCH]
  - 偏好设置中"是否启用归档"的默认值 属于 [M14 ONBOARD_PREFS]
  - 应用退出时的数据保护与崩溃恢复属于 [M15 APP_RELIABILITY]

## 2. 目标用户与场景

### 主要用户画像

- **CLI 重度用户**：每天和 Claude Code 聊几十轮，担心一两个月之后想回看某次方案讨论时记录已经被自动清理。
- **方案沉淀者**：会把和 AI 的对话当成项目知识库，常常需要把某次"完整推理过程"导出成 Markdown 贴进飞书 / Notion / 周报。
- **跨工具用户**：同时使用 Claude Code 和 Codex，希望两边的对话都能被 Muxvo 一并保留，不用记两个地方。
- **新手**：刚装 Muxvo，没意识到原生对话会过期，需要一个明确的提示告诉他"Muxvo 在帮你长期保留"。

### Top3 使用场景

**场景 1 — 长期保留**：用户上个月和 Claude Code 一起做过一次重要的架构推演，今天想回看。原生位置的文件可能已经被清理，用户打开 Muxvo 聊天历史后依然能看到那次对话，意识到"幸好开了归档"。

**场景 2 — 把对话发给同事**：用户和 Claude 来回讨论了一个 bug，最终修好了。用户想把这段对话整理给同事，于是右键会话选择"导出为 Markdown"，导出文件自动保存到固定目录，用户点击"在 Finder 中显示"后直接拖进聊天工具。

**场景 3 — 首次启用**：用户第一次打开聊天历史，看到顶部一条横幅说明："Claude Code 本地对话只保留约 30 天，Muxvo 已自动帮你长期保留到本机。"用户对照说明确认归档开关确实是开启状态，关掉横幅继续浏览。

### 使用频率

- **同步**：完全后台进行。用户每次打开聊天历史都会被动感知一次（看到底部"最后同步 HH:MM"），但绝大多数时候不需要主动操作。
- **导出**：偶尔。重度用户每周 1-3 次，普通用户每月数次。
- **首次引导横幅**：仅一次（用户主动关闭后不再出现）。

## 5. 详细需求条目

### REQ-CHAT_SYNC-001 自动归档开关

**触发方式**：用户在聊天历史面板顶部的归档说明横幅右侧看到"自动归档"开关，点击它。
**前置条件**：用户已经打开聊天历史面板。
**正常流程**：
  1. 用户点击开关
  2. 文案立即在"自动归档：开启"和"自动归档：关闭"之间切换
  3. 后台搬运任务相应地恢复或停止
**用户看到的反馈**：开关图标与文案同步切换，无加载等待、无弹窗。
**结束状态**：用户停留在面板上，开关呈现新的状态。
**异常情况**：偏好写入失败 → 开关回弹到原状态，无错误弹窗（用户重试即可）。
**相关**：[M14-REQ-NNN]（首次引导决定该开关的初始默认值）。

### REQ-CHAT_SYNC-002 归档说明横幅

**触发方式**：用户首次（或卸载后再次安装后第一次）打开聊天历史面板。
**前置条件**：用户从未点击过横幅右侧的关闭按钮。
**正常流程**：
  1. 面板加载完成
  2. 顶部出现一条浅色横幅，文案为预设说明（见 §7.4）
  3. 横幅右侧显示开关与关闭按钮
**用户看到的反馈**：横幅以静态出现，不滑动不闪烁。
**结束状态**：用户读完说明后可以选择关闭横幅、切换开关或忽略它继续浏览列表。
**异常情况**：无。
**相关**：[M08-REQ-NNN]（聊天历史面板的整体进入路径）。

### REQ-CHAT_SYNC-003 后台搬运的进度反馈

**触发方式**：Muxvo 在后台开始搬运任务（启动时、或运行中检测到原生位置有新对话）。
**前置条件**：归档开关处于"开启"且横幅尚未被用户关闭。
**正常流程**：
  1. 用户看到横幅文案变为"正在归档 12/87..."
  2. 数字随后台推进而递增
  3. 全部搬运完成后约 2 秒，文案恢复为默认说明
**用户看到的反馈**：纯文案变化，无进度条动画，无弹窗。
**结束状态**：横幅回到默认状态，列表中陆续出现新搬运过来的会话。
**异常情况**：单条搬运失败 → 进度数字仍然推进，跳过的条目下次自动补；用户无感知。
**相关**：REQ-CHAT_SYNC-006、REQ-CHAT_SYNC-022。

### REQ-CHAT_SYNC-005 同步过程中可正常浏览

**触发方式**：Muxvo 启动后用户立即打开聊天历史面板。
**前置条件**：后台正在进行批量搬运。
**正常流程**：
  1. 用户点击项目、点击会话 → 页面正常响应
  2. 已经搬运到长期保留区的内容立刻可见
  3. 还没搬运到的内容会在搬运过程中陆续出现在列表里
**用户看到的反馈**：列表内容自然增长，无强制刷新、无加载遮罩、无"请等待同步完成"提示。
**结束状态**：搬运全部结束后，列表保持当前最新一致状态。
**异常情况**：无。
**相关**：REQ-CHAT_SYNC-022、[M08-REQ-NNN]。

### REQ-CHAT_SYNC-006 单条失败不影响整体

**触发方式**：后台搬运遇到某条对话临时无法读取（例如被原生 CLI 占用）。
**前置条件**：归档已开启，搬运任务正在进行。
**正常流程**：后台跳过这一条 → 进度数字照常前进 → 下一次后台搬运自动重试这一条。
**用户看到的反馈**：无错误弹窗、无红色高亮，进度文案保持平滑。
**结束状态**：被跳过的对话最终在某次后续搬运中成功保留。
**异常情况**：连续多次失败 → 仍然静默跳过，用户依然能在原生 CLI 一侧看到原文件。
**相关**：REQ-CHAT_SYNC-003。

### REQ-CHAT_SYNC-008 启动时自动补全缺失对话

**触发方式**：用户每次打开 Muxvo。
**前置条件**：归档处于开启状态。
**正常流程**：
  1. Muxvo 启动时与原生位置进行一次比对
  2. 把比对结果中"原生有但长期保留区还没有"的对话自动搬运过来
  3. 用户进入聊天历史时看到完整列表
**用户看到的反馈**：第一次打开聊天历史面板时若仍在搬运，则横幅显示进度，否则直接看到完整列表。
**结束状态**：用户能在 Muxvo 看到与原生 CLI 一致的全部历史。
**异常情况**：原生位置不存在 → 用户看到 [M08] 的"未检测到 Claude Code"空态。
**相关**：[M08-REQ-NNN]。

### REQ-CHAT_SYNC-010 仅归档会话可正常查看

**触发方式**：用户在会话列表中点击一条原生侧已被清理、只剩长期副本的会话。
**前置条件**：该会话此前曾经被自动搬运。
**正常流程**：
  1. 用户点击该会话
  2. 右栏正常加载并显示完整内容
  3. 用户像普通会话一样浏览、复制、导出
**用户看到的反馈**：与普通会话**完全一致**，没有"仅备份"红字、没有功能裁剪。
**结束状态**：用户停留在右栏，可以查看任意一条历史。
**异常情况**：长期副本本身意外丢失 → 进入空态："会话内容暂时无法显示"。
**相关**：REQ-CHAT_SYNC-011、[M08-REQ-NNN]。

### REQ-CHAT_SYNC-011 仅归档会话可继续聊天

**触发方式**：用户在右栏顶部点击"继续聊天"按钮。
**前置条件**：当前选中的是一条仅存在于长期保留区的会话，且 Muxvo 还能读取到它的工作目录。
**正常流程**：
  1. 用户点击"继续聊天"
  2. Muxvo 先把这条对话送回到 Claude Code 的原生位置
  3. 在新终端中以"继续这条会话"的方式打开 Claude Code
**用户看到的反馈**：约 1-2 秒等待后用户进入终端，看到 Claude Code 已经接管这条历史。
**结束状态**：用户已经在终端里继续这条对话。
**异常情况**：恢复失败（磁盘满 / 权限问题） → 按钮恢复可点状态，控制台或日志中可查具体原因，用户界面无弹窗。
**相关**：[M01-REQ-NNN]（终端创建）、[M08-REQ-NNN]（"继续聊天"按钮位置）。

### REQ-CHAT_SYNC-012 右键单会话导出为 Markdown

**触发方式**：用户在会话列表中右键点击一张会话卡片，菜单中选择"导出"。
**前置条件**：该会话至少包含一条消息。
**正常流程**：
  1. 用户右键 → 弹出菜单（"重命名 / 导出 / 删除"等）
  2. 用户点击"导出"
  3. Muxvo 把整段对话写入 Markdown 文件
  4. 完成后自动弹出文件管理器并高亮该文件
**用户看到的反馈**：约 0.5 - 2 秒后系统打开文件管理器窗口，所选文件被高亮。
**结束状态**：用户看到导出文件，可以拖拽 / 转发 / 打开。
**异常情况**：导出目录无写入权限 → 提示"导出失败，请检查目录权限后重试"，文件管理器不会被打开。
**相关**：REQ-CHAT_SYNC-014、REQ-CHAT_SYNC-016、REQ-CHAT_SYNC-018。

### REQ-CHAT_SYNC-013 顶部按钮复制会话为 Markdown

**触发方式**：用户在右栏会话详情上方的工具区点击"复制会话为 Markdown"按钮。
**前置条件**：右栏当前有一段已加载完成的会话。
**正常流程**：用户点击按钮 → Muxvo 把整段对话拼成 Markdown 放入剪贴板 → 按钮文案短暂变为"已复制！"。
**用户看到的反馈**：文案动效 1-2 秒后恢复。
**结束状态**：用户可以直接粘贴到任意编辑器或聊天工具。
**异常情况**：剪贴板被系统拒绝写入 → 文案不变，无报错（用户重试即可）。
**相关**：REQ-CHAT_SYNC-012。

### REQ-CHAT_SYNC-014 导出文件名规则

**触发方式**：用户执行任意一次导出。
**前置条件**：用户已经选中要导出的会话。
**正常流程**：取出会话标题（用户重命名过的优先，否则用对话首句生成的默认标题） → 截取前 50 个字符 → 把 `/`、`\`、`:`、`*`、`?`、`"`、`<`、`>`、`|` 等非法字符替换为 `_` → 拼上扩展名 `.md` 或 `.json`。
**用户看到的反馈**：文件名一眼可读，例如 `修复终端跳顶问题的讨论.md`。
**结束状态**：文件命名稳定，不会出现空文件名或乱码。
**异常情况**：标题完全为空 → 退化使用会话内部编号作为文件名。
**相关**：REQ-CHAT_SYNC-012。

### REQ-CHAT_SYNC-016 导出后在文件管理器中高亮

**触发方式**：导出动作完成。
**前置条件**：导出成功，文件已写入磁盘。
**正常流程**：Muxvo 自动调用系统文件管理器 → 打开导出目录 → 把刚导出的文件设为高亮选中。
**用户看到的反馈**：用户看到熟悉的 Finder / 资源管理器窗口，目标文件被框选。
**结束状态**：用户可以直接拖拽文件到任意目的地。
**异常情况**：用户没有打开文件管理器的权限 → 跳过这一步，仅保留"已导出"提示。
**相关**：REQ-CHAT_SYNC-012、REQ-CHAT_SYNC-017。

### REQ-CHAT_SYNC-018 导出失败提示

**触发方式**：导出过程中任意一步失败。
**前置条件**：用户已经发起导出动作。
**正常流程**：系统检测到失败 → 界面短暂出现一条提示"导出失败，请检查目录权限后重试" → 约 3 秒后自动消失。
**用户看到的反馈**：提示位于面板底部或右栏顶部，无遮挡，无需手动关闭。
**结束状态**：用户回到面板，可以再次尝试导出。
**异常情况**：连续多次失败 → 同样只是再次出现提示，不会升级为弹窗。
**相关**：REQ-CHAT_SYNC-012。

### REQ-CHAT_SYNC-019 导出 JSON 供后续处理

**触发方式**：开发者用户在高级菜单中选择"导出为 JSON"（首发期为隐藏入口或仅右键菜单提供）。
**前置条件**：用户已经选中一个会话。
**正常流程**：用户选择 JSON 格式 → Muxvo 把会话完整结构写入文件 → 文件保存到与 Markdown 同一个导出目录，扩展名为 `.json`。
**用户看到的反馈**：与导出 Markdown 完全一致（"已导出 + 文件管理器高亮"）。
**结束状态**：用户得到一份结构化文件供二次加工。
**异常情况**：与 Markdown 导出一致。
**相关**：REQ-CHAT_SYNC-012。

## 9. 边界、限制与异常

- **数量限制**：单次导出文件名最长 50 个字符；导出格式当前仅支持 Markdown 与 JSON 两种。
- **明确不支持**：
  1. 不支持把多条会话一次性合并导出成同一个文件（每条会话独立成文件）
  2. 不支持选择导出目录（首发期固定保存在 Muxvo 的导出目录）
  3. 不支持导出时自定义模板（首发期固定 Markdown 排版）
  4. 不支持把图片作为附件单独导出
  5. 不支持导出为 PDF / Word / HTML
  6. 不支持把搬运过的对话同步回原生 CLI 的"自动覆盖"模式（仅"继续聊天"时手动恢复）
  7. 不支持删除"仅归档"的会话副本（首发期不提供 UI 入口，需要用户手动清理目录）
- **错误提示文案**：
  - "导出失败，请检查目录权限后重试。"
  - 删除会话前的确认："确定删除此聊天记录？删除后无法恢复。"
- **数据丢失风险**：
  - 用户主动关闭归档后，原生侧新增的对话不会再被保留 → 用户感受到的保障措施是开关文案明确写"自动归档：关闭"
  - 卸载应用时若用户手动选择删除整个保留目录 → 用户感受到的保障措施是默认卸载流程不删该目录
  - 长期保留区被外部程序破坏 → Muxvo 启动时会自动重新搬运一份能找到的最新对话

## 10. 明确不做的事（Out of Scope）

1. **导出 PDF**：版式与字体处理复杂，首发期仅 Markdown / JSON。等用户呼声足够强烈再做。
2. **批量导出**：首发只支持单会话导出。等用户开始问"能不能一次导一周的对话"时再考虑。
3. **自定义导出目录**：首发期固定路径以减少出错概率。
4. **导出含原始图片附件**：图片在 Markdown 中以行内方式呈现已可满足主流诉求。
5. **同步进度的精细可视化**（进度条 / 百分比环）：当前文案"X/Y"已经够用。
6. **跨设备同步**：本模块只做"本机长期保留"，跨机/跨账号同步属于云端方向。
7. **Gemini CLI 的归档**：当前仅 Claude Code + Codex 两源；Gemini 等待官方对话格式稳定后再纳入。
8. **将归档目录暴露在 UI 中可视浏览**：避免用户误删。

## 11. 附：术语与跨模块引用

### 11.1 本模块独有术语

| 术语 | 定义 |
|---|---|
| **归档** | Muxvo 把 Claude Code / Codex 在原生位置的对话整本搬到本机长期保留区的行为 |
| **长期保留区** | Muxvo 用来长期保存对话副本的本机区域；用户不需要知道具体路径 |
| **仅归档会话** | 原生位置已被清理，但 Muxvo 长期保留区仍有完整副本的会话 |
| **后台搬运** | 用户无感知地把对话从原生位置写入长期保留区的过程 |
| **导出** | 用户主动把某条会话写成独立 Markdown 或 JSON 文件的动作 |

### 11.2 引用的其他模块

- [M01-REQ-NNN]：终端创建（继续聊天后开新终端）
- [M08-REQ-NNN]：聊天历史面板的进入路径与列表浏览
- [M09-REQ-NNN]：搜索结果中的会话同样可被导出
- [M14-REQ-NNN]：偏好设置中"自动归档"的初始默认值
- [M15-REQ-NNN]：应用退出时的搬运任务收尾

### 11.3 待确认项

- **JSON 导出入口的可见性**：首发期是否对所有用户暴露，还是仅在偏好打开"开发者模式"时显示？待与产品对齐。
- **长期保留区上限**：是否需要给用户一个"占用空间提醒"（如超过 1 GB 时提示）？待产品决定。
- **导出后是否自动复制路径到剪贴板**：备选的"导出 + 复制路径"行为，是否作为快捷选项？待与产品对齐。
- **Gemini CLI 的接入时间表**：与 [M08] 的多源接入计划一并确认。
