# M07 EDITOR_SEND – 输入发送与反馈 PRD

> 版本 v1.0 · 适用 Muxvo Rust 重构 · 行数预算 340-460 行

## 1. 模块定位

- **一句话**：用户把编辑器里写好的文字（可能还带着图片）按一下 Enter，就能稳稳送进终端，并立刻知道送成功了还是没送出去。
- **不用它会怎样**：用户写完 prompt 按 Enter，等半天不知道送没送出去；送出去的多行 prompt 在 Claude Code 里断成一行行分别被当作独立请求；网络抖动时发送失败却没有任何提示，用户以为发出去了，其实 Claude Code 什么也没收到。
- **与相邻模块的分界**：
  - "按 Enter / Cmd+Enter 触发发送、发送中的视觉反馈、发送后的清空、发送失败的提示与重试" 属于本模块
  - "编辑器里怎么写字、换行、撤销、草稿保留" 属于 [M05 EDITOR_INPUT]
  - "图片附件的五种状态（贴进来、保存中、附加好、移除、失败）" 属于 [M06 EDITOR_ATTACH]
  - "发送后终端主区如何显示、光标如何移动、回显" 属于 [M01 TERM_LIFECYCLE]
  - "发送后 Claude Code / Codex 回复的 Dock 角标、终端红点" 属于 [M04 TERM_NOTIFY]

## 2. 目标用户与场景

### 主要用户画像

- **Claude Code / Codex 重度用户**：每天要按几十次发送键，每次发送内容少则几行、多则几百行。对"按下 Enter 后的 200 毫秒之内有没有反馈"非常敏感——一旦有一次"按下去像没反应"，就会怀疑自己漏按或程序死了。
- **Shell 用户**：只敲一行短命令，按 Enter 立刻执行。对发送的心智只有一条："Enter 就送，干脆利落，别有多余动画"。
- **新手**：第一次用 Muxvo，不清楚 Enter 是换行还是发送，会本能地先按一下 Enter 看看会发生什么；也会因为"写了半行不满意"想用 Esc 之类的键撤回。

### Top3 使用场景

**场景 1 — 发送一条长 prompt 给 Claude Code**：用户写完一段 30 行的 prompt，按 Enter。期望这 30 行作为"同一条消息"被 Claude Code 收到，而不是被当成 30 条。发送瞬间输入区清空，终端主区立刻看到 Claude Code 开始思考的反馈。

**场景 2 — 发送失败后重试**：用户按了 Enter 但终端此刻刚好在重启、或者前台工具正卡着没准备好。用户看到输入区内容没清空，下方多出一行红色提示"发送失败，按 Enter 重试"。用户等一秒钟再按 Enter，这一次送进去了，输入区清空，红色提示消失。

**场景 3 — 发送带图片的消息**：用户从截图工具粘贴了一张图进编辑器，又写了两行说明文字，按 Enter。期望图片和文字作为一次发送被 Claude Code 接收。如果图片还没保存好就按了 Enter，Muxvo 会自动等图片就绪再发送，不会把图片漏掉只发文字。

### 使用频率

日常极高频。Claude Code 用户每天按 30-80 次发送键；Shell 用户每天按 100+ 次；发送失败与重试是偶尔（每周 1-3 次），但一旦发生必须被用户立刻感知。

## 5. 详细需求条目

### REQ-EDITOR_SEND-001 Enter 触发发送

**触发方式**：用户在编辑器可见形态下，焦点在输入区，按 Enter（不含 Shift、不含 Cmd/Ctrl）。
**前置条件**：输入区内至少存在一个字符，或至少附加了一张图片；发送按钮未被锁定（即没有正在进行的发送）。
**正常流程**：
  1. 用户写完内容
  2. 用户按 Enter
  3. 编辑器在 150 ms 内内容淡出
  4. 输入区回到空态占位
  5. 终端主区看到刚送出的内容被前台 CLI 接收
**用户看到的反馈**：输入区内容淡出；发送瞬间输入区边框有一次极轻微的高亮闪动；输入区文字清空后占位文案重新出现；终端主区可能出现刚发出的 prompt 或命令的回显（属于 [M01]）。
**结束状态**：空态，光标留在输入区，用户可以直接敲下一条。
**异常情况**：终端未就绪时进入 REQ-EDITOR_SEND-008 的失败分支；内容超过硬上限时进入 REQ-EDITOR_SEND-014 的确认分支；图片正在保存时进入 REQ-EDITOR_SEND-013 的延迟分支。
**相关**：[M05-REQ-003] · REQ-EDITOR_SEND-007 · REQ-EDITOR_SEND-011

### REQ-EDITOR_SEND-004 空内容按 Enter 不发送

**触发方式**：用户在空的编辑器里按 Enter。
**前置条件**：输入区字符数为 0，且没有任何附加图片。
**正常流程**：
  1. 用户按 Enter
  2. 系统判断内容为空
  3. 什么都不发生
**用户看到的反馈**：占位文案继续显示；不闪烁、不弹提示、不播放任何声音；边框无变化。
**结束状态**：编辑器保持空态。
**异常情况**：如果用户反复按 Enter，始终不会触发任何动作，避免误按出现"幽灵消息"。
**相关**：REQ-EDITOR_SEND-005 · [M05-REQ-008]

### REQ-EDITOR_SEND-008 发送失败后保留内容

**触发方式**：用户按 Enter 触发发送，但送不出去。
**前置条件**：终端未就绪 / 前台进程刚刚退出 / 内容过大被拒 / 其他未知异常。
**正常流程**：
  1. 用户按 Enter
  2. 发送过程内部判断失败
  3. 输入区内容**不清空**，保持原样
  4. 输入区下方出现一行红色提示条
  5. 提示条包含原因文案和"按 Enter 重试"引导
**用户看到的反馈**：红色底色一行文字，宽度与输入区对齐；文字包含失败原因和重试指引；输入区边框不变化；光标继续留在编辑器里。
**结束状态**：用户可以直接修改内容后重发，也可以原样再按一次 Enter 重试。
**异常情况**：连续三次失败后，红色提示条右侧额外出现"复制内容"链接，方便用户把写好的内容先复制走避免丢失。
**相关**：REQ-EDITOR_SEND-009 · REQ-EDITOR_SEND-010 · REQ-EDITOR_SEND-017 · REQ-EDITOR_SEND-019

### REQ-EDITOR_SEND-012 不同 CLI 发送体感一致

**触发方式**：用户在不同 CLI（Claude Code / Codex / Gemini CLI / 普通 Shell）前台下按 Enter。
**前置条件**：前台工具已启动并正常监听输入。
**正常流程**：
  1. 用户按 Enter
  2. Muxvo 识别当前前台是哪种 CLI
  3. Muxvo 用对应 CLI 能理解的方式把文字（和图片）送进去
  4. 用户只看到"输入区清空 + 终端主区看到消息被接收"，其余细节对用户透明
**用户看到的反馈**：四种 CLI 下的"按 Enter 清空输入区"动画一致；清空速度一致；占位文案恢复速度一致；失败时的红条样式也一致。用户不需要记住"发给 Claude Code 是一种键、发给 Shell 是另一种键"——都是 Enter。
**结束状态**：所有 CLI 下体验一致，用户心智单一。
**异常情况**：
  - 如果前台是 Gemini CLI 且带图片，而 Gemini CLI 不支持剪贴板图片，Muxvo 会自动改用文件路径方式，用户看到的差异只是 Gemini CLI 自己对图片的回复形式不同。
  - 如果前台是 Shell 且用户粘贴图片，图片会以文件路径形式出现在命令行（详见 [M06-REQ-013]），用户对此有心理预期（Shell 本身不认识图片）。
**相关**：REQ-EDITOR_SEND-011 · [M06-REQ-010] · [M06-REQ-013]

### REQ-EDITOR_SEND-013 图片未就绪时延迟发送

**触发方式**：用户粘贴图片后，图片还在"保存中"状态，用户立刻按 Enter。
**前置条件**：至少一张图片处于"附加中"状态（详见 [M06-REQ-006]）。
**正常流程**：
  1. 用户按 Enter
  2. Muxvo 检测到有图片未就绪
  3. 输入区进入"发送中"视觉状态（边框变成稍暗的灰色，发送按键暂时不响应新的 Enter）
  4. 图片保存完成后
  5. Muxvo 自动完成发送
  6. 输入区清空回空态
**用户看到的反馈**：按 Enter 瞬间内容不立刻消失；边框变灰表示"在等着"；最长约 2 秒后图片保存完成，内容和缩略图一起淡出。
**结束状态**：空态。
**异常情况**：如果 2 秒后图片仍未就绪，进入失败分支（REQ-EDITOR_SEND-008），文案为"图片保存超时，请重新粘贴"。
**相关**：[M06-REQ-006] · [M06-REQ-008] · REQ-EDITOR_SEND-015

### REQ-EDITOR_SEND-014 超长内容发送前确认

**触发方式**：用户在编辑器里积累了超过硬上限（约 50 万字）的内容后按 Enter。
**前置条件**：内容字数超过软上限时只显示字数胶囊（见 [M05-REQ-027]），超过硬上限时才触发本需求。
**正常流程**：
  1. 用户按 Enter
  2. 弹出居中对话框"输入非常长"
  3. 正文一句话说明可能影响响应速度
  4. 两个按钮："继续发送" / "取消"
  5. 用户按"继续发送" → 内容被送出；按"取消" → 返回编辑状态，内容不动
**用户看到的反馈**：对话框遮住其他区域，内容清晰；"继续发送"按钮作为主操作；"取消"为次要。
**结束状态**：发送成功 → 空态；取消 → 内容原样保留。
**异常情况**：确认后发送仍然失败时走 REQ-EDITOR_SEND-008 的错误分支。
**相关**：[M05-REQ-027] · REQ-EDITOR_SEND-008

### REQ-EDITOR_SEND-015 发送中状态视觉

**触发方式**：用户按 Enter 后，发送在 400 ms 内没完成。
**前置条件**：发送进行中。
**正常流程**：
  1. 用户按 Enter
  2. 400 ms 后仍未完成
  3. 输入区边框变稍暗灰色，内容半透明、暂不可编辑
  4. 发送成功 → 清空；失败 → 走 REQ-EDITOR_SEND-008
**用户看到的反馈**：边框暗化渐变；内容半透明；再次按 Enter 无反应。
**结束状态**：取决于发送结果。
**异常情况**：发送中按 Ctrl+C 按穿透规则送到终端，发送本身不被取消。
**相关**：REQ-EDITOR_SEND-013 · REQ-EDITOR_SEND-016 · [M05-REQ-020]

## 6. 主要用户旅程

### Journey 1：新手第一次发送一条消息

1. **你** 第一次打开 Muxvo，默认终端 + Claude Code 前台
   → **你所见**：输入区显示"给 Claude Code 写点什么，Enter 发送，Shift+Enter 换行"
   → **你感受**：一眼看懂
2. **你** 敲"帮我看一段代码"再按 Enter
   → **你所见**：内容在 150 ms 内淡出，占位文案回来；终端主区出现刚发送的内容被 Claude Code 接收的反馈
   → **你感受**：跟手，像聊微信一样
3. **你** 试探性地在空输入区再按一次 Enter
   → **你所见**：什么都没发生
   → **你感受**：放心，不会发出空消息
4. **你** 写"第一步"+Shift+Enter+"第二步"+Shift+Enter+"第三步"，按 Enter
   → **你所见**：三行作为一条消息送给 Claude Code，输入区清空
   → **你感受**：比在终端里手动续行方便多了

### Journey 2：老手发送带图片的长 prompt

1. **你** 在输入区写了 15 行 prompt，从截图工具复制一张图按 ⌘V
   → **你所见**：缩略图出现在输入区（详见 [M06]）
2. **你** 按 Enter
   → **你所见**：
     - 图片已保存好：文字和缩略图一起淡出，输入区清空
     - 图片还在保存中：边框变稍暗灰色，内容半透明约 1 秒，然后自动清空
   → **你感受**：完全不用关心"图片有没有准备好"
3. **你** 继续在空输入区写下一条 prompt
   → **你所见**：立刻能打字，没有"发送中锁定"的尴尬
   → **你感受**：顺滑

### Journey 3：发送失败后的重试

1. **你** 写好一段 prompt，但这个终端前台工具刚好崩溃
2. **你** 按 Enter
   → **你所见**：内容**没有**被清空；下方出现红色提示"发送失败：终端未就绪。按 Enter 重试"
   → **你感受**：心里一紧，但知道发生了什么
3. **你** 等前台工具自动重启后再次按 Enter
   → **你所见**：内容淡出，红色提示消失，输入区回到空态
   → **你感受**：松一口气，内容没白写
4. **你** 如果连续失败 3 次
   → **你所见**：红色提示条右端多出"复制内容"链接
   → **你感受**：最坏情况我可以先把内容复制出来保存

## 7. 界面规格

### 7.1 页面/面板清单

| 名称 | 作用 | 进入方式 | 退出方式 |
|---|---|---|---|
| 输入区（正常态） | 写内容、按 Enter 发送 | 新建终端 / 切到编辑器可见的终端 | 发送成功 / 切终端 / 全屏工具 |
| 输入区（发送中态） | 告知用户正在发送，不接受再次 Enter | 按 Enter 后 400 ms 内发送未完 | 发送成功 / 发送失败 |
| 发送失败提示条 | 告知用户失败原因并引导重试 | 发送失败 | 再次发送成功 / 用户清空内容 |
| 超长确认对话框 | 让用户确认是否发送巨量内容 | 按 Enter 时内容超过硬上限 | 点"继续发送"或"取消" |

### 7.2 各页关键区域

- **输入区（正常态）**：内容区可编辑（含缩略图，由 [M06] 管理），边框在有焦点时淡色高亮；超长时右下角出现字数胶囊（属于 [M05]）。
- **输入区（发送中态）**：边框变稍暗灰色，内容半透明，光标暂停闪烁。
- **发送失败提示条**：紧贴输入区下方，红色文字 + 浅红底色，宽度与输入区对齐；连续失败 3 次后右端追加"复制内容"链接。
- **超长确认对话框**：居中标题 + 说明正文 + 主操作"继续发送" + 次操作"取消"。

### 7.3 五态规格（发送相关）

| 状态 | 用户看到什么 | 可做的动作 |
|---|---|---|
| **空态** | 输入区空、占位文案在、边框灰 | 开始写字；按 Enter 无任何反应 |
| **加载态** | 按 Enter 后 400 ms 以上未完成：边框变暗灰、内容半透明 | 等待；不可再次触发发送；可按 Ctrl+C 穿透到终端 |
| **正常态** | 输入区有内容、可编辑、边框高亮 | 编辑、按 Enter 发送、按 Shift+Enter 换行 |
| **错误态** | 内容留在输入区，下方一行红色失败提示 | 修改内容重发；原样按 Enter 重试；连续失败 3 次后可点"复制内容" |
| **受限态** | 终端已关闭 / 处于全屏工具形态 | 输入区不可见或整体置灰，发送功能暂时不可用 |

### 7.4 文案示例

> 空态占位（Claude Code）："给 Claude Code 写点什么，Enter 发送，Shift+Enter 换行"
> 空态占位（Codex）："向 Codex 提问，Enter 发送，Shift+Enter 换行"
> 空态占位（Gemini CLI）："让 Gemini CLI 帮你做什么？Enter 发送"
> 空态占位（普通命令行）："输入命令，Enter 执行，Shift+Enter 多行"
> 发送失败（终端未就绪）："发送失败：终端未就绪，按 Enter 重试"
> 发送失败（前台未响应）："发送失败：对方暂时没有响应，按 Enter 重试"
> 发送失败（图片保存超时）："发送失败：图片保存超时，请移除后重新粘贴"
> 发送失败（连续三次后追加）："发送失败：对方暂时没有响应，按 Enter 重试 · 复制内容"
> 超长确认标题："输入非常长"
> 超长确认正文："当前输入约 52 万字，发送后可能需要较长时间响应。确定继续？"
> 超长确认按钮："继续发送" / "取消"
> 发送中提示（静默模式）：边框暗化 + 内容半透明，不出现文字

## 8. 状态与交互规则

### 8.1 可见状态清单

- **输入区空态**：占位文案、边框灰
- **输入区有内容态**：占位消失、光标闪烁、边框有焦点时高亮
- **输入区发送中态**：边框暗化、内容半透明、不接受再次 Enter
- **输入区错误态**：内容保留、下方红色提示条
- **输入区受限态**：整体置灰、不可交互

### 8.2 状态切换触发

- 用户按 Enter 且内容为空 → 保持空态（无任何变化）
- 用户按 Enter 且内容非空 → 进入"发送中" →（400 ms 内完成）正常态 → 空态
- 用户按 Enter 且发送超过 400 ms → 显式"发送中"视觉（边框暗化、内容半透明）
- 发送成功 → 输入区清空 → 空态
- 发送失败 → 内容保留 + 错误态红条
- 错误态下再次按 Enter → 进入"发送中"（若失败仍然停留错误态，只是文案可能变化）
- 错误态下连续失败 3 次 → 红条右端出现"复制内容"链接
- 错误态下用户把内容全部删除 → 错误态红条消失，回到空态
- 超长内容按 Enter → 弹确认对话框 →（继续发送）"发送中" →（取消）正常态保留内容
- 用户按 Shift+Enter → 只换行，不发送
- 用户按 Cmd+Enter / Ctrl+Enter → 与 Enter 等效，触发发送
- 用户按 Esc → 没有任何反应
- 用户按 ↑/↓ → 光标移动，不调历史

### 8.3 快捷键与手势

| 按键/手势 | 作用 | 前置条件 |
|---|---|---|
| Enter | 触发发送 | 编辑器可见 + 焦点在输入区 + 内容非空或有附件 + 未处于"发送中" |
| Cmd+Enter / Ctrl+Enter | 触发发送（与 Enter 等效） | 同上 |
| Shift+Enter | 换行（不触发发送） | 编辑器可见 + 焦点在输入区 |
| Esc | 不触发任何发送相关操作 | 编辑器可见 |
| ↑ / ↓ | 光标行内/跨行移动（不调历史） | 编辑器可见 |
| "复制内容"链接（连续失败 3 次后出现） | 把当前输入内容复制到系统剪贴板 | 连续失败 ≥3 次 |
| "继续发送" / "取消"按钮 | 超长确认对话框的两个选项 | 超长确认对话框已弹出 |

### 8.4 多窗口/多标签行为

- 每个终端有自己独立的发送状态：终端 A 正在"发送中"时，终端 B 可以同时被用户按 Enter 发送。
- 多窗口之间互不干扰：窗口 1 终端的发送失败提示条不会出现在窗口 2 的编辑器里。
- 用户同时在多个终端触发"连续失败 3 次"时，每个终端独立计数，各自显示自己的"复制内容"链接。

## 9. 边界、限制与异常

### 数量 / 频率限制

- 连续触发发送的最小间隔与"发送中"状态锁定绑定：只要一次发送未结束，Enter 不会再次触发新的发送。
- "发送中"状态最长显示 10 秒（10 秒后如果仍未结果，自动切到错误态并提示"发送超时"）。
- 连续失败 3 次后追加"复制内容"链接；连续成功一次后重新归零。
- 超长硬上限约 50 万字；软上限约 1 万字（软上限只影响字数胶囊显示，不影响发送）。
- 发送中状态的显式视觉反馈阈值为 400 ms：400 ms 内完成不显式闪现"发送中"，避免频闪。

### 明确不支持

- 不支持"发送历史上下翻"（按 ↑/↓ 调出已发送过的 prompt）
- 不支持"定时发送"/"倒计时发送"
- 不支持"发送中主动取消"按钮（发送中只能按 Ctrl+C 穿透到终端）
- 不支持"只发送部分选中内容"——Enter 始终发送全部
- 不支持"发送成功 toast"
- 不支持"已发送历史回看面板"（终端主区自带回显）
- 不支持"发送前二次确认"除非触发超长硬上限
- 不支持"用 Esc 取消正在撰写的内容"——清空请用 ⌘A + Delete

### 错误提示文案

> "发送失败：终端未就绪，按 Enter 重试"
> "发送失败：对方暂时没有响应，按 Enter 重试"
> "发送失败：图片保存超时，请移除后重新粘贴"
> "发送失败：内容超过对方可接受的大小，请缩短后重发"
> "发送超时：对方 10 秒内没有回应，按 Enter 重试"
> "输入非常长：当前输入约 52 万字，发送后可能需要较长时间响应。确定继续？"

### 数据丢失风险

- **风险 1**：失败时用户误以为已发出。保障：失败时**绝不清空**输入区，红色提示条不可忽略。
- **风险 2**：发送中突然关闭终端/退出 Muxvo。保障：未完成的发送计为失败，内容作为草稿下次恢复（[M05-REQ-015]）。
- **风险 3**：连续失败用户放弃。保障：3 次后出现"复制内容"链接，内容可先保留到剪贴板。
- **风险 4**：发送一半丢失。保障：Muxvo 只在"已被完整接收"后才清空输入区。

## 10. 明确不做的事（Out of Scope）

- **不做**：发送历史上下翻。**为什么**：与编辑器的 ↑/↓ 光标移动语义冲突。**何时考虑**：后续专门设计"历史面板"时。
- **不做**：发送中主动取消按钮。**为什么**：一次已交给对方的发送无法撤回，做假按钮只会误导；中断可用 Ctrl+C 穿透。**何时考虑**：不考虑。
- **不做**：定时发送 / 倒计时发送。**为什么**：超出终端工作流，属于脚本化需求。**何时考虑**：未来 Skill 场景。
- **不做**：发送成功提示 toast。**为什么**：成功是默认路径，打扰代价大于信息量。**何时考虑**：不考虑。
- **不做**：发送失败时自动重试。**为什么**：自动重试可能与用户修改冲突，可能在不合适的时机重复发送。**何时考虑**：不考虑。
- **不做**：多终端批量发送同一段内容。**为什么**：超出单终端编辑器职责。**何时考虑**：未来"广播到多终端"场景。
- **不做**：发送时的声音反馈。**为什么**：高频操作，声音会成为噪音。**何时考虑**：不考虑。

## 11. 附：术语与跨模块引用

### 11.1 本模块独有术语

| 术语 | 定义 |
|---|---|
| 发送 | 用户按 Enter / Cmd+Enter 触发的动作，把编辑器的全部内容（文字 + 附件）一次性送给当前终端前台 |
| 发送中态 | 按 Enter 之后、还没完成之前的过渡状态，边框暗化、内容半透明、不接受再次 Enter |
| 发送失败提示条 | 出现在输入区下方的一行红色文字，说明失败原因并引导重试 |
| 软上限 | 触发字数胶囊显示的长度阈值，不影响能否发送 |
| 硬上限 | 触发发送前确认对话框的长度阈值，用户需要主动确认才能继续发送 |
| 静默成功 | 发送成功后不弹任何成功 toast，只以"输入区清空"作为信号 |

### 11.2 引用的其他模块

- [M04 TERM_NOTIFY] 发送后等待响应时的红点/Dock 角标
- [M05-REQ-003] Enter 发送的编辑器端定义
- [M05-REQ-006] 多行输入
- [M05-REQ-008] 空态占位文案
- [M05-REQ-015] Muxvo 重启后草稿恢复
- [M05-REQ-020] Ctrl+C 穿透到终端
- [M05-REQ-027] 超长字数胶囊
- [M06-REQ-006] 图片附加中状态
- [M06-REQ-010] 图片已附加
- [M06-REQ-013] 非 CC 场景下的文件路径回退

### 11.3 待确认项

- **待确认 1**：发送中显式视觉阈值（400 ms）与超时阈值（10 秒）的具体数值需与设计对齐。
- **待确认 2**：连续失败出现"复制内容"链接的次数阈值（当前 3 次）是否合理。
- **待确认 3**：超长硬上限（当前 50 万字）需与不同 CLI 的真实处理能力对齐。
- **待确认 4**：Cmd+Enter 与 Ctrl+Enter 的跨平台映射是否需要在偏好设置里可调（见 [M14 ONBOARD_PREFS]）。
- **待确认 5**："图片保存超时"的默认等待时长（当前 2 秒）是否足够覆盖一般尺寸截图。
- **待确认 6**：连续失败计数何时归零——当前是"任何一次成功归零"，是否还需按时间窗口归零。
