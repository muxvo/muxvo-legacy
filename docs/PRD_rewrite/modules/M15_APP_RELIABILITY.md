# M15 APP_RELIABILITY – 应用生命周期与异常 PRD

> 版本 v1.0 · 适用 Muxvo Rust 重构 · 行数预算 550 行（±15%）

## 1. 模块定位

- 一句话说明：这个模块定义用户打开、关闭、崩溃恢复、更新、遇到错误时的"全局感受"。
- 不用该模块用户会损失什么：没有统一的启动 / 退出 / 报错规范，用户会面对风格各异的对话框、不知道什么时候能关、遇到问题无从下手、关错时丢工作。
- 与相邻模块的分界：
  - 应用整体启动流程 / 关闭确认 / 崩溃恢复 / 更新提示 / 离线基调 / 错误对话框视觉规范 属于本模块
  - 单个终端关闭的确认对话框（有运行中进程时）属于 [M01 TERM_LIFECYCLE]
  - Dock 角标的等待输入模式属于 [M04 TERM_NOTIFY]；Dock 角标的总开关属于 [M14 ONBOARD_PREFS]

## 2. 目标用户与场景

- **主要用户画像**：
  - **日常使用者**：每天打开 Muxvo 处理多个终端任务，关心"打开快不快"、"关不关得掉"、"会不会丢数据"。
  - **偶发用户**：几天打开一次，关心"上次的东西还在吗"、"有新版本吗"。
  - **网络不稳定用户**：在酒店/机场/家中 Wi-Fi 漂移的环境，关心"断网时还能不能用"。

- **Top3 使用场景**：
  - **场景 1（首次打开）**：用户双击 Dock 图标，预期在几秒内看到主界面；如果是第一次，应有引导；如果不是第一次，上次留下的终端应自动出现，不用重新配置。
  - **场景 2（一天结束关掉）**：用户点关闭按钮，如果还有终端在跑，应被提醒"这些东西会被终止"，给一次后悔的机会；关掉后下次打开能回到差不多的状态。
  - **场景 3（出错时）**：用户遇到问题（某个终端挂了 / 网断了 / 磁盘满了 / 更新下载失败），期望看到一句人话解释 + 一个明确下一步，而不是一堆乱码堆栈。

- **使用频率**：日常 + 全局。本模块的需求在用户每次打开、关闭、切页面时都可能触发，是 Muxvo 的"底色"。

## 5. 详细需求条目

### REQ-APP_RELIABILITY-001 启动画面

**触发方式**：用户双击 Dock 图标 / 应用图标 / 从命令行启动
**前置条件**：无
**正常流程**：
  1. 用户双击图标
  2. Dock 中出现 Muxvo 图标并弹跳
  3. 在不超过 1 秒内出现一个带 Muxvo 标志的主窗口（非白屏）
  4. 主窗口加载完毕后自动替换成正常界面
**用户看到的反馈**：深色背景 + Muxvo 文字标志 + 轻微淡入动画
**结束状态**：用户停留在主界面或欢迎引导
**异常情况**：
  - 启动超过 5 秒：用户仍只看到启动画面，不会看到白屏
**相关**：[M14-REQ-001]（首次启动走欢迎引导）

### REQ-APP_RELIABILITY-002 启动时长感知

**触发方式**：打开 Muxvo
**前置条件**：无
**正常流程**：
  1. 首次启动 ≤ 5 秒出现欢迎引导
  2. 非首次启动 ≤ 3 秒出现主界面
  3. 若超过 3 秒仍未进入主界面，启动画面持续显示（不允许空白）
**用户看到的反馈**：启动画面中央可出现一个轻微旋转的圆点作为"在加载"提示
**结束状态**：主界面或欢迎引导
**异常情况**：
  - 卡死：启动超过 15 秒仍停留在启动画面 → 用户感受到异常，可直接强制退出重试（见 §9）
**相关**：[M14-REQ-001]

### REQ-APP_RELIABILITY-003 恢复上次终端

**触发方式**：打开 Muxvo 时存在上次保存的终端列表
**前置条件**：上次正常退出或崩溃退出后，终端记录未被手动清空
**正常流程**：
  1. 进入主界面
  2. 按上次的顺序逐个恢复终端，终端标签 / 名称 / 工作目录保持一致
  3. 每个终端的状态点从"正在启动"变为正常
**用户看到的反馈**：终端格子按顺序逐个出现
**结束状态**：用户看到与上次关闭前几乎一样的主界面
**异常情况**：
  - 某个终端的工作目录已被删除：该终端以红色状态点出现，旁边带"重启"按钮（见 [M01]）
  - 所有终端都恢复失败：显示空主界面，无错误弹窗
**相关**：[M01-REQ-NNN]（终端重启），[M14-REQ-NNN]（启动终端数量偏好）

### REQ-APP_RELIABILITY-004 恢复上次窗口尺寸位置

**触发方式**：打开 Muxvo
**前置条件**：上次用户调整过窗口尺寸或位置
**正常流程**：用户打开应用 → 窗口以上次的宽高和位置出现
**用户看到的反馈**：窗口位置与上次一致
**结束状态**：主窗口可见并获得焦点
**异常情况**：
  - 上次的屏幕已断开（外接显示器拔掉）：窗口回到主屏幕居中位置，不会跑到屏幕外
**相关**：无

### REQ-APP_RELIABILITY-005 崩溃后自动恢复

**触发方式**：上次 Muxvo 因意外原因（崩溃 / 强杀 / 断电）退出
**前置条件**：用户再次打开 Muxvo
**正常流程**：
  1. 打开应用
  2. 上次正在运行的终端自动出现
  3. 偏好设置 / 主题 / 语言等保持一致
**用户看到的反馈**：与正常恢复相同的终端格子
**结束状态**：用户看到与上次相同的工作区
**异常情况**：
  - 终端记录文件损坏：以空主界面打开，用户偏好仍保留
**相关**：REQ-APP_RELIABILITY-006, [M14-REQ-NNN]

### REQ-APP_RELIABILITY-006 崩溃恢复提示

**触发方式**：系统检测到上次是非正常退出
**前置条件**：同上
**正常流程**：用户看到主界面顶部中央出现一行浅灰横幅"已从上次意外关闭中恢复"
**用户看到的反馈**：一行浅灰字体，无关闭按钮，5 秒后自动淡出
**结束状态**：横幅消失，用户继续使用
**异常情况**：无
**相关**：REQ-APP_RELIABILITY-005

### REQ-APP_RELIABILITY-007 关闭确认：有活跃终端

**触发方式**：用户点击窗口关闭按钮 / 按系统快捷键退出 / 右键 Dock "退出"
**前置条件**：至少有 1 个终端正在运行
**正常流程**：
  1. 用户点关闭
  2. 窗口不立刻关闭，弹出标题为"退出 Muxvo"的对话框
  3. 对话框正文显示"当前有 N 个终端正在运行，退出后将全部终止。"
  4. 用户点"退出"则应用关闭；点"取消"则返回主界面
**用户看到的反馈**：
  > 标题："退出 Muxvo"
  > 正文："当前有 3 个终端正在运行，退出后将全部终止。"
  > 按钮："取消" / "退出"
**结束状态**：退出 → 应用关闭；取消 → 回到主界面
**异常情况**：
  - 再次点关闭：重新弹出同一对话框
**相关**：REQ-APP_RELIABILITY-009, REQ-APP_RELIABILITY-010

### REQ-APP_RELIABILITY-008 关闭确认：无活跃终端

**触发方式**：用户点关闭，当前无任何终端
**前置条件**：终端数 = 0
**正常流程**：同上，但正文为"确定要退出 Muxvo 吗？"
**用户看到的反馈**：
  > 正文："确定要退出 Muxvo 吗？"
  > 按钮："取消" / "退出"
**结束状态**：同 REQ-007
**异常情况**：无
**相关**：REQ-APP_RELIABILITY-007

### REQ-APP_RELIABILITY-009 关闭确认 Esc 取消

**触发方式**：关闭确认对话框显示中
**前置条件**：对话框处于焦点
**正常流程**：用户按 Esc → 对话框关闭 → 应用继续运行
**用户看到的反馈**：对话框淡出动画
**结束状态**：回到主界面
**异常情况**：无
**相关**：REQ-APP_RELIABILITY-007

### REQ-APP_RELIABILITY-010 关闭前保存工作区

**触发方式**：用户在关闭确认对话框选"退出"
**前置条件**：关闭被确认
**正常流程**：
  1. 记录当前终端列表、窗口尺寸与位置
  2. 关闭所有终端
  3. 窗口消失
**用户看到的反馈**：关闭过程不超过 2 秒
**结束状态**：应用退出
**异常情况**：
  - 某个终端无响应：超过 2 秒仍未退出的终端被强制终止，用户不会卡在退出状态
**相关**：REQ-APP_RELIABILITY-003

### REQ-APP_RELIABILITY-011 单窗口行为

**触发方式**：Muxvo 已在运行时，用户再次双击图标
**前置条件**：已有一个 Muxvo 窗口
**正常流程**：
  1. 不出现新窗口
  2. 已有窗口被带到最前
  3. 如果之前被最小化，现在被恢复
**用户看到的反馈**：已有窗口获得焦点
**结束状态**：用户看到原窗口
**异常情况**：无
**相关**：无

### REQ-APP_RELIABILITY-012 更新后台下载

**触发方式**：后台检测到新版本
**前置条件**：用户联网
**正常流程**：
  1. 自动开始下载
  2. 下载过程不打断用户任何操作
  3. 下载完成后下次启动应用时自动应用新版本
**用户看到的反馈**：菜单栏右侧出现下载指示（见 REQ-013）
**结束状态**：更新已就绪，等待下次重启生效
**异常情况**：
  - 下载失败 → REQ-016
**相关**：REQ-APP_RELIABILITY-013

### REQ-APP_RELIABILITY-013 更新进度指示

**触发方式**：更新下载开始
**前置条件**：同上
**正常流程**：用户看到菜单栏右侧出现一个 24 像素左右的圆形指示，内部为一个箭头图标，外圈随下载进度填满
**用户看到的反馈**：下载中圆环按百分比填充；默认状态下该指示只在下载期间出现
**结束状态**：REQ-015 或 REQ-016
**异常情况**：无
**相关**：REQ-APP_RELIABILITY-014

### REQ-APP_RELIABILITY-014 更新详情悬停

**触发方式**：用户将鼠标悬停到下载指示上
**前置条件**：下载中或刚完成
**正常流程**：用户看到气泡提示
**用户看到的反馈**：
  > 标题："正在下载更新..."
  > 进度条 + "12.3 MB / 45.6 MB"

## 6. 主要用户旅程

### Journey 1：首次打开 Muxvo

1. **你** 双击 Muxvo 图标
   → **你所见**：Dock 图标弹跳，约 0.3 秒后出现带 Muxvo 标志的深色启动画面
   → **你感受**：有反馈，不会怀疑是不是启动失败
2. **你** 等待约 2 秒
   → **你所见**：启动画面被欢迎引导替换
   → **你感受**：被带着走，不用猜该点哪里
3. **你** 点"开始引导"
   → **你所见**：进入主界面，菜单栏顶部出现 Muxvo 标题 + 各个标签
   → **你感受**：知道"终端"、"Skills"、"聊天"都在哪
4. **你** 点 +
   → **你所见**：第一个终端出现
5. **你** 点关闭按钮
   → **你所见**：弹窗"当前有 1 个终端正在运行，退出后将全部终止。"
   → **你感受**：被提醒过了，不会误关
6. **你** 点"取消"
   → **你所见**：弹窗消失，终端还在

### Journey 2：每日使用中途遇到新版本

1. **你** 正在操作某个终端
   → **你所见**：菜单栏右侧悄悄出现一个圆形下载指示
   → **你感受**：没被打断
2. **你** 把鼠标移上去
   → **你所见**：气泡显示"正在下载更新... 12.3 MB / 45.6 MB  1.2 MB/s"
3. **你** 继续工作几分钟
   → **你所见**：圆形指示变成绿色对勾，悬停显示"v1.3.0 下载完成 / 下次启动时自动更新"
4. **你** 3 秒后不再关注它
   → **你所见**：指示淡出消失
5. **你** 晚上结束工作，点关闭按钮
   → **你所见**：关闭确认弹窗，点"退出"
6. **你** 第二天重新打开
   → **你所见**：主界面出现约 2 秒后"更新内容"弹窗，列出本版本新增条目
   → **你感受**：知道为什么界面有变化

### Journey 3：断网 + 某终端崩溃 + 应用崩溃恢复

1. **你** 正在用 2 个终端跑命令
2. **你** 家里 Wi-Fi 突然断了
   → **你所见**：菜单栏下方出现橙色横幅"当前离线，部分功能不可用"
   → **你感受**：知道是网络问题，不是 Muxvo 坏了
3. **你** 想打开聊天历史
   → **你所见**：本地已同步的聊天仍可看
4. **你** 其中一个终端前台进程崩溃
   → **你所见**：该终端状态点变红，出现"重启"按钮（[M01]）；另一个终端不受影响
5. **你** 点"重启"
   → **你所见**：终端恢复正常
6. **你** 此时 Muxvo 本身因某种原因被强杀
   → **你所见**：窗口突然消失
7. **你** 重新双击图标
   → **你所见**：主界面恢复，2 个终端都被自动拉回；顶部出现一行浅灰提示"已从上次意外关闭中恢复"
   → **你感受**：没丢工作，松一口气
8. **你** 5 秒后浅灰提示自动消失
9. **你** Wi-Fi 恢复
   → **你所见**：橙色横幅淡出

- 卡顿浮层：隐藏 / 显示 / 超时态
- 错误对话框：三档（信息 / 警告 / 错误）× 显示 / 隐藏

### 8.2 状态切换触发

- 用户双击图标 → 看到启动画面
- 主界面加载完 → 启动画面消失
- 用户点关闭按钮且有终端 → 看到"有 N 个终端"关闭确认
- 用户点关闭按钮且无终端 → 看到"确定退出"关闭确认
- 用户按 Esc 或点"取消" → 关闭确认消失
- 用户点"退出" → 窗口关闭
- 后台检测到新版本 → 下载指示出现
- 下载完成 → 指示变绿 → 3 秒后淡出
- 下载失败 → 指示变红 → 3 秒后淡出
- 首次进入新版本主界面 → 2 秒后弹出更新内容
- 网络断开 → 顶部出现离线横幅
- 网络恢复 → 横幅淡出
- 内存过阈值 → 内存告警出现
- 内存降下 → 下次检查后消失
- 非正常退出 → 下次打开时显示崩溃恢复提示条
- 操作 > 3 秒无响应 → 卡顿浮层出现

### 8.3 快捷键与手势

| 按键/手势 | 作用 | 前置条件 |
|---|---|---|
| Esc | 关闭关闭确认对话框 / 更新内容弹窗 / 错误对话框 | 对话框显示中 |
| 点击菜单栏空白 + 拖动 | 移动整个窗口 | 非全屏 |
| 悬停菜单栏下载指示 | 显示详情气泡 | 指示显示中 |
| 点击外部区域 | 关闭更新内容弹窗 | 弹窗显示中 |

### 8.4 多窗口/多标签行为

- 同时只允许一个 Muxvo 主窗口。用户再次双击图标 / 命令行再次启动 → 原窗口被带到前台，不会出现第二个窗口
- 多标签（终端 / Skills / 聊天 / 文件）在同一窗口内切换，标签之间共享同一份状态，无跨窗口同步需求

## 9. 边界、限制与异常

- **数量限制**：
  - 同时运行的 Muxvo 主窗口：1 个
  - 启动画面最长允许显示：15 秒（超过则用户需强制退出重试）
  - 关闭时等待终端清理最长：2 秒（超时后强制终止）
  - 卡顿浮层"处理中"最长显示：15 秒后文案升级

- **明确不支持**：
  - 多窗口并排使用
  - 后台常驻（关闭窗口 = 完全退出）
  - 系统托盘图标 / 菜单栏驻留图标
  - 关闭后仍保留终端在后台运行
  - 用户手动点击触发立即检测更新（仅后台定期检测）

- **错误提示文案**：
  - 启动阶段无法读取终端记录 → 以空主界面打开，不弹错误对话框（降级处理）
  - 某个终端恢复失败 → 按 [M01] 的"红色状态点 + 重启按钮"处理，不弹全局错误
  - 更新下载失败 → 菜单栏红色叉 + "下载失败"悬停文案，不弹窗
  - 离线 → 顶部橙色横幅"当前离线，部分功能不可用"，不弹窗
  - 内存过高 → 黄色三角 + "内存占用较高，建议关闭部分终端"，不弹窗
  - 非正常退出 → 浅灰提示条"已从上次意外关闭中恢复"，不弹窗
  - 操作卡顿 → 卡顿浮层，不弹窗
  - 严重错误（如本地日志目录无法写入）→ 错误档对话框："无法写入日志目录 / 请检查磁盘空间或权限"
  - 统一原则：**凡是能降级的都不弹窗，只有需要用户立刻决定的才弹错误对话框**

- **数据丢失风险**：
  - 崩溃时：终端记录已实时保存，下次打开可恢复
  - 关闭时：关闭确认保证用户被告知"有 N 个终端将被终止"，给出后悔机会
  - 更新时：下次启动才真正应用新版本，不会打断当前工作
  - 明确告知用户：**终端运行中的未保存数据（如某命令正在运行尚未落盘）不在恢复范围内**

## 10. 明确不做的事（Out of Scope）

- **不做**：多窗口并排工作（两个 Muxvo 窗口同时打开）
  - 为什么不做：当前主用户画像为单屏工作者，多窗口带来复杂的数据同步问题
  - 什么条件下再考虑：用户反馈量 ≥ 30 且明确提出需求

- **不做**：系统托盘驻留 / 后台隐藏运行
  - 为什么不做：Muxvo 是重交互工具，驻留会诱发"以为已退出实则仍占资源"的错觉
  - 什么条件下再考虑：引入推送通知后再评估

- **不做**：用户手动触发"立即检查更新"按钮
  - 为什么不做：后台定期检测已能覆盖 99% 场景，多一个按钮反而增加困惑
  - 什么条件下再考虑：用户明确反馈"想立刻升级"

- **不做**：崩溃时弹出"崩溃上报"对话框让用户确认
  - 为什么不做：打扰用户，应默认静默收集或完全不收集
  - 什么条件下再考虑：引入主动反馈机制后

- **不做**：离线时禁用所有页面（给用户一种"Muxvo 离线就不能用"的错觉）
  - 为什么不做：Muxvo 的终端 / 本地文件 / 本地聊天是完全离线可用的
  - 什么条件下再考虑：永不

- **不做**：用户可在关闭确认对话框里选择"保留终端到下次启动"vs"清空"
  - 为什么不做：默认就是"保留到下次启动"，让用户决定反而增加心智负担
  - 什么条件下再考虑：用户明确反馈希望"每次打开都是干净环境"

- **不做**：应用内内建日志查看器
  - 为什么不做：日志受众是高级用户，直接打开文件夹足以
  - 什么条件下再考虑：用户反馈"找不到日志"比例 > 10%
